# ADR-0173: The changelog's release sections are generated from the history

## Context

ADR-0148 moved `CHANGELOG.md` out of the repository root to `docs/CHANGELOG.md`
and deferred generating its `## [Unreleased]` section, with the measurements for
doing so. The deferral was honest about two things it could not have, and left
one question open.

What it could not fix: a section of 1038 lines hand-merged from merge to merge
by a rule no gate touched, with 79 commits touching it in the 17 days after
`v0.3.0`. Moving the file did not remove the thing that rotted it.

The two measured blockers were real. A **merge-scoped** generated section is not
a per-merge gate: the inputs that name what shipped change when the merge
lands, so 107 merges since `v0.3.0` means a `--write`, a follow-up commit and a
red lane in between on essentially every merge — the cost ADR-0134 took off the
merge path on purpose. And the **bead queue** is not in a checkout: `.beads/` is
gitignored and lives in the git common dir, so a section generated from bead
metadata would run in the developers' worktrees and silently not run in the CI
job that follows every merge.

The open question was: *what committed input, identical on a feature branch and
on `main`, can answer "what shipped since the last release"?*

It is the commits. A work commit already carries the bead id in a `Task:`
trailer (ADR-0152), the bead title as its subject, the `ADR-NNNN` ids the change
cites and the narrative the agent wrote for it; `tools/bd-merge-bead.py` writes
`Merge <bead>: <title>` on the merge commit that brings it in. That is a git-only
input: the same bytes on a feature branch, on `main` and in a CI clone. The
bead *description* is not in it, and does not need to be — the release entry is
the title, the ids and the narrative, and the bead is still the queue's.

## Decision

**Generate the release sections from the history, at release time, and delete
the `## [Unreleased]` section rather than regenerate it.**

### 1. The input is a git range

`tools/changelog.py --range <previous tag>..HEAD --date YYYY-MM-DD --write`
renders one `## [<Version>] - <date>` section and writes it above the newest
release in `docs/CHANGELOG.md`. The version is read from `<Version>` in
`Directory.Build.props`, so `RELEASING.md` steps 2 and 3 stay one edit. `--print`
renders without writing; `--verify-release <version>` re-renders a committed
release section from `<previous tag>..v<version>` and reports whether the file
still says what the history says.

One entry per bead, newest first in `git log` order, with the full title taken
from the merge subject where there is one (a work subject is truncated to a line
often enough to be a worse title), the bead id and the `ADR-NNNN` ids as its
provenance, and the work commits' bodies as the narrative with the trailer
block cut. A commit with no bead of its own is still an entry, with its short
hash, because it still shipped.

### 2. Generation happens once per release, and the merge path is untouched

Nothing is generated between releases. That is the whole reason this decision is
usable on the merge path: with no generated section in the tree between
releases, no merge owes a `--write` and no lane is red waiting for one. The
range a release renders is the history that accumulated since the last tag, and
the file between releases simply carries released sections.

### 3. The check is the hand-merge, not a comparison

`tools/changelog.py --check` fails on a `## [Unreleased]` heading in
`docs/CHANGELOG.md` and on nothing else. It is the rule that is true on every
merge, so it cannot red a merge that did not hand-merge anything — the property
the two rejected designs both lacked. A check that fails whenever the committed
text differs from the generated text fails on every merge, which is why the
generated-and-compared shape of ADR-0141 (the ADR register) does not transfer
here: that artefact is regenerated by the same change that changes it, and a
release section is regenerated by a release.

Every lane of `eng/verify.sh` and the CI `verify` job call it directly, beside
`tools/doc_surface.py`, `tools/conflict_markers.py` and
`tools/trailing_whitespace.py`, because hand-merging is a **docs** change and a
rule that runs only when `tools/**` changed is not a gate (ADR-0143, ADR-0146).

### 4. Two details that make a range renderable at both ends

The commit that carries a release is named by a `Release: <version>` trailer
(`RELEASING.md` step 5) rather than by an assumption that the tag sits on the
tip, so rendering `v0.3.0..HEAD` before the tag and `v0.3.0..v0.4.0` after it
give the same section — the release commit is never an entry inside itself.

`--verify-release` reports *not judged* rather than failing when a tag is not in
the clone it reads, which is every default CI clone. The same reasoning ADR-0148
§5 applied to the bead queue applies to the tag list: a check that fails on a
missing input is a false red on the job that follows every release.

## Alternatives

**Generate the `## [Unreleased]` section on every merge and gate the
difference.** Rejected on ADR-0148's own measurement: 107 merges since `v0.3.0`
means a `--write` commit per merge plus a red lane in between. It re-imposes on
the merge path the cost ADR-0134 removed from it, for a documentation file.

**Gate a stale generated section (the ADR-0141 shape).** Rejected for the same
reason, one step removed: the comparison is red on every merge, because the
range moves when the merge lands. ADR-0141 works because the ADR register is
regenerated *by the change that changes it*; a release section is regenerated by
a release, months later.

**Generate from the bead queue (`bd show`) with a hand-committed manifest.**
Rejected as CI-invisible: `.beads/` is gitignored and lives in the git common
dir, so a rule that reads it runs in the developers' worktrees and does not run
in the job that follows every merge — a false green in the direction ADR-0143
and ADR-0146 are about.

**Keep the hand-merge and add a gate that only checks the heading and the
version.** Rejected: it holds the shape and not the rot. The entries were
hand-written per merge, and nothing about a heading check notices an entry that
was forgotten or written twice.

**Keep the section, generated at release time into `## [Unreleased]` for the
*next* release to cut.** Rejected: it is the same artefact one step earlier, so
it is stale for the same reason and its staleness is invisible.

## Not decided

Whether a release entry should carry more than the commits do. A bead's
description is richer than the narrative a work commit carries, and it is not
in git; a release that wants the long form pastes it into the released section
by hand, where it is frozen history. Whether that stays a habit or becomes a
rule — a committed per-bead release note, written once at close, generated from
— is open, and it is the only way this decision gets *more* provenance without
a per-merge write.

Whether `--verify-release` should run in CI. It cannot without
`fetch-depth: 0` and the tag list; the tag list is the blocker, not the depth.

## Consequences

- **1038 lines of hand-merged section are gone**, and with them the 79 commits'
  worth of hand-editing that rotted them. The pending work it described is not
  lost: every entry's title, ids and narrative are in the commits that landed
  it, and the next release renders them.
- **A merge costs nothing** for the changelog, which is the point: the merge
  path is unchanged, and a lane can afford a check that is true on every merge.
- **"What shipped since the last release" is a `git log` between releases** and
  a generated section after one. That is the same answer the root documents
  gave for in-flight state (ADR-0148): `bd` and `git log`, not a file.
- **The narrative in a release note is the commit body**, which is written for
  the reader of the commit rather than for a release audience. It is
  deliberately faithful and it is shorter than a bead description; a release
  that wants more edits the released section, which is frozen.
- **The gate can only see the hand-merge**, not an entry written wrongly inside
  a release section. `--verify-release` closes that at release time and only
  when the tags are there.
- **`docs/CHANGELOG.md` is now a generated artefact** in the way
  `architecture/decisions/README.md` is (ADR-0141), and it is checked the same
  way it is produced: by the release step that writes it.
