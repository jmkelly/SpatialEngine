# ADR-0052: The Spatial CLI is a declarative public-API client

## Context

Automating the engine today means either driving the HTTP API by hand,
using one of the two typed SDKs from application code, or running the
network-dependent seed script (`tools/seed/seed.mjs`). None of those is a
comfortable surface for an LLM or a shell script that wants to *set up* a
workspace: add a dataset, build a map out of layers, style it, and then
hand back FeatureServer/MapServer endpoints. The engine already has every
verb needed for that (ADR-0041 ingest + publications; ADR-0047 persisted
style; ADR-0048/0051 projections), but no first-class command-line client
that composes them and describes the result.

Two questions are architectural rather than mechanical:

1. **Where does the CLI sit?** It must not reach into the host's DI
   container or call providers directly — principle 2 (headless engine),
   principle 14 (agents and humans use the same public services), and
   ADR-0033 all say the CLI is a client of the public HTTP API, exactly
   like `tools/seed/seed.mjs` and the workbench.
2. **How is a workspace stored and generalised?** "Add datasets, create
   maps with layers and styles, then emit a FeatureServer or MapServer"
   is one model, not three. The engine already models it as a
   `Publication` with a `PublicationKind` (Feature/Map/Image). The CLI
   needs a portable, declarative document that captures the same thing so
   it can be reviewed, versioned and replayed.

An LLM-facing CLI has two further requirements that shape the decision:
descriptive, self-documenting flags and a machine-readable (`--json`)
mode with stable exit codes. Pulling in a parser package (for example
`System.CommandLine`) is possible but unnecessary; the engine's value
lies in the composition, and a dependency-free parser keeps the tool
publishable as one file and keeps the architecture allowlist untouched.

## Decision

**1. `Spatial.Cli` is a pure client of the public host API.**

A new console project lives at `clients/dotnet/Spatial.Cli` (outside
`src/`, beside `Spatial.Client`, not a member of the engine solution). It
references `Spatial.Client`, `Spatial.Core` and `Spatial.PluginSdk` only,
holds no spatial algorithm and no provider, and talks to a host over
HTTP. Like `tools/seed/seed.mjs`, every mutation flows through the neutral
admin API (`POST /api/ingest`, `PUT/DELETE /api/publications`) and every
read through the public routes. It is configuration-free beyond a host
URL, an admin token and a project-file path.

**2. A *spatial project file* is the portable, declarative workspace.**

A versioned JSON document (default `spatial.json`) describes what a
workspace wants to exist:

- **datasets** — id, SRID, source (local path or `http(s)` URL), format,
  identity mode and optional source SRID for engine-side reprojection;
- **maps** — name, kind (`feature` | `map` | `image`), store, description,
  copyright, and ordered layers;
- **layers** — dataset, optional display name, geometry family and a
  compact draw recipe (`color`, `opacity`, `lineWidth`, `radius`,
  `visible`).

The CLI can `project apply` (idempotent: reuse existing datasets and
publications, preserve stable layer ids per ADR-0041) and `project export`
(serialise the host's current datasets and publications back to a file).
The project file is data, not code; the same document can be hand-written,
generated by an LLM, or produced by `export`.

**3. Map kind selects the projection; the CLI emits the endpoints.**

A project map lowers one-to-one to a `Publication`: `feature` →
FeatureServer, `map` → MapServer, `image` → ImageServer (ADR-0035/0048/
0051). `map export` and `project export` therefore return the correct
GeoServices root URL for each map, alongside the machine-readable
publication. Nothing new is invented on the wire: the CLI composes
existing neutral concepts and reports their projections.

**4. The compact draw recipe lowers to the persisted MapLibre fragment.**

`color`/`opacity`/`lineWidth`/`radius`/`visible` plus a geometry family
lower to the same JSON array of MapLibre style-layer objects that
`tools/seed/seed.mjs` and the workbench composer produce (ADR-0044/0047),
injected at the host as `source-layer`. The lowering is deterministic and
covered by golden tests, so CLI-authored, seed-authored and
composer-authored services draw identically.

**5. Descriptive flags, dependency-free parser, machine-readable output.**

Options are long and self-describing (`--dataset`, `--srid`,
`--source-srid`, `--identity-field`, `--layer`, `--geometry`, `--color`,
`--opacity`, `--line-width`, `--radius`, `--description`, `--copyright`),
`--help` renders from the command catalog, `--json` emits a stable
`{ ok, command, data }` / `{ ok:false, error:{ code, message } }`
envelope, and `--dry-run` previews a mutation. The parser is hand-written;
the CLI takes no third-party packages. Exit codes are stable:
`0` success, `2` invalid arguments, `3` not found, `4` store/host
unavailable, `5` cancelled, `1` unexpected.

**6. Secrets stay on the config channel.**

Host and admin token come from `--host`/`--token` or `SPATIAL_HOST`/
`SPATIAL_ADMIN_TOKEN` only, are never echoed in output or error messages,
and never appear in the project file (which may be committed). This
matches the ADR-0041 rule that connection material is config-only.

**7. Tests are unit-first, with the real host as an integration proof.**

The command layer is tested against a fake gateway (no network) and the
project file, style lowering and parser have focused unit tests. A
container-free end-to-end run against a real host is the release proof,
mirroring `eng/e2e-web.sh`.

## Consequences

- New projects: `clients/dotnet/Spatial.Cli` (not in the solution) and
  `tests/unit/Spatial.Cli.Tests` (in the solution, which builds and
  quality-gates the CLI). No platform/implementation allowlist entries
  change; no `src/` project gains a dependency.
- The project-file schema is a new on-disk contract. It is versioned
  (`version: 1`) and the CLI refuses unknown versions with
  `invalid.arguments`; broadening it is a compatible addition.
- `tools/seed/seed.mjs` stays as the network-dependent demo seeder; the
  CLI is the general, offline-or-online workspace tool. The two share the
  draw-recipe lowering rule, which is pinned by tests on each side.
- The CLI is a client and never a server: it adds no route, no contract
  type and no host configuration. Publishing it as one self-contained
  binary is a build concern (`dotnet publish`), not an architecture one.
- The GeoServices admin projection (ADR-0041) remains the Esri-shaped
  alternative for tools that need it; the CLI deliberately uses the
  neutral API instead.

## Alternatives

- **Import the host's DI container and call providers in-process.**
  Violates principle 2/14 and couples the CLI to every implementation.
  Rejected.
- **Take a parser package (`System.CommandLine`).** Adds a dependency and
  version churn for a surface that is mostly routing; the
  dependency-free parser keeps the single-file publish and the allowlist
  simple. Rejected for v1; revisitable if the surface grows.
- **One command shape per protocol (a `feature` group and a `map` group).**
  Duplicates the layer/style model and re-introduces the split ADR-0041
  removed. Rejected; `PublicationKind` is the single axis.
- **Store the workspace only on the host.** The host already persists
  publications, but datasets carry ingest parameters the registry does not
  keep; a portable project file is what an LLM or a repository check-in
  actually needs. Both exist.
